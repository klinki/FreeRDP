## Exact matrix and implementation differences

All 80 planned trials ran once: independent loss of 0%, 25%, 50% or 70%
in each direction, active reliable DATA limits 16/32/48/64 and seeds
11/29/47/71/101. Each direction was shaped to 10 Mbit/s, 15 ms one-way
delay, uniform ±1 ms jitter, a 30 ms shaper queue and 28-byte UDP/IP
wire overhead. There was no additional duplication, reordering or blackout.
The sending endpoint used a 131072-byte owned-payload budget and 16384-byte
bulk records, alongside 64-byte probes scheduled at 20 Hz. The peer limit
stayed 64. Warmup/measurement/drain were 5/30/12 seconds; the variant order
was deterministically shuffled. Both endpoints loaded the same frozen PR
library. Plan, source hashes, actual flight peaks and endpoint receipts are
retained. Equal random seeds do not imply identical losses of logical DATA
when the traffic generated by the implementations differs.

The PR has LogWindow 15, 32767 advertised capacity, 64 usable physical
send slots, and a 1208-byte maximum DATA payload at wire MTU 1232. The
local adapter used LogWindow 7, 128 slots with 127 usable entries and
1132-byte DATA payloads. The cap restricts only new logical DATA admission;
PR ACK, RTO, retry, receive and timer policies are preserved. Its incoming
LogWindow is observed but does not gate its native v3 send policy. The
compatibility `recovery_mode=fast` environment value is ignored by the PR
adapter. These are implementation comparisons, not an isolated experiment
on one ACK/RTO change.

The private adapter drives production `rdpudp_send` / `rdpudp_check` and
receives through the original callback. Optional backend identity, unified
native failure state, queue/flight observers and a separate adapter-driver
error distinguish evidence availability. Unsupported separate send/receive
failure and loss-report counters are null. Normal builds without
`WITH_RDP_BENCH` have no private benchmark exports.

At 25% the local matrix verified 19 streams and completed 14 trials; the
PR verified nine streams and completed none. At 50% and 70% both matrices
failed every trial. The PR does not resolve these high-loss failures in
this raw transport workload. Larger limits do not establish a safe
throughput/latency improvement; zero-loss limit 64 has poor diagnostic
tails and incomplete evidence.

An additional unloaded probe-only check (outside the matrix, 1/5/5 seconds,
zero loss, cap 32, seed 11) observed all 120 scheduled probes for each
implementation. Local p95/p99 was 33.715/35.754 ms with valid relay timing.
PR observed 46.573/98.220 ms but relay dispatch p99 was 51.177/61.873 ms,
so the PR unloaded result is timing-invalid. Loaded probe latency includes
bulk queue residence, admission blocking and reliable stream ordering;
it is not the configured 30 ms propagation RTT or visual desktop latency.
The sanity audit initially referenced the historical local source manifest;
its retained correction re-audits the same sealed samples against the
actual common Python harness hashes, without rerunning or changing samples.

The next useful work is a reliable timing environment and targeted PR
recovery tracing, using the retained failure seeds. The current comparison
is evidence against treating the PR as a demonstrated high-loss cure;
it does not isolate a transport root cause or justify tuning a production
packet limit from these mostly invalid measurements.
