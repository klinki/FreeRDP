## Two different rejection causes

Relay lateness is the actual post-send monotonic timestamp minus the scheduled dispatch time. The schedule already includes bandwidth serialization, 15 ms propagation, and ±1 ms jitter. The acceptance limit is `max(0.5 ms, 10% of one-way delay)`, or 1.5 ms here, applied separately to each direction's nearest-rank p99. It uses whole-trial deliveries, including warmup and drain. It is neither probe RTT nor a comparison against the configured 15/30 ms propagation delay.

There are real dispatch deviations: 44 forward and 37 reverse directional rejections overlap into 50 trials. All 158 nonempty directional samples fit within the 200,000-sample reservoir, so no reservoir sampling affects these percentiles. Twenty-seven directions had at most 99 deliveries, making nearest-rank p99 their maximum; 13 of those failed.

The worst trial, zero loss / 48 packets / seed 71, recorded forward/reverse p99 lateness of 266.215/224.074 ms and maximum forward lag of 2.126 seconds. Its manifest records one-minute host load of 245.729 on a 10-logical-CPU Apple M4. The preceding startup timeout recorded load 194.261. These endpoints consumed only 1.077 and 1.720 CPU seconds over the worst trial's 47-second schedule. Host load is not CPU utilization and was sampled only at trial start. It strongly suggests external/system scheduling or resource interference, but does not identify a process, QoS, power, or kernel mechanism.

The unloaded PR probe control also recorded 51.177/61.873 ms relay p99 with zero retries and low endpoint CPU. The local control 13 seconds later recorded 1.137/1.015 ms. The 6,720-packet/s headroom test used immediate, unshaped dispatch: it proves throughput, not accurate 15 ms timed wakeups. Endpoints run in separate processes; their `ctypes.CDLL` calls release their own GIL, and no native/relay lock is shared. The retained main trials lack per-dispatch traces, relay-thread CPU/scheduling history, and thermal or process profiles. The evidence cannot support a more specific OS cause or an assertion that the PR itself caused the relay pauses.

The queue observer has a concrete range defect. Its 16,384 bins of 125,000 ns cover only 2.048 seconds. Any residence or admission sample at or above that duration clears a shared observer-valid flag. Python converts this to “native queue observer invalid,” Type1 labels it a harness failure, and the dashboard calls generic qualification `timing_valid`.

All 47 invalid observers have actual histogram overflow and zero clock, segment, and arithmetic-counter errors. Thirty-five coincide with native FAILED; 12 do not, including nine fully verified streams. Queue/admission maxima reach 2.706, 8.292, 16.683, and 14.401 seconds across the four loss levels. Long recovery/backpressure waits exceeded our instrument's range; they are not additional hardware clock failures. The observer flag affects measurement availability, not native ACK/RTO policy. Only two trials remain COMPLETE-qualified because service failures persist; this audit does not manufacture passes or reconstruct out-of-range queue percentiles.

For comparison, the historical local matrix had 66 relay dispatch rejections and six observer rejections, with five overlaps, yielding 67 generic rejections. Comparing 71 against 67 as pure timing counts was incorrect.

## Comparison with the PR's claims

[Tester Ceschi-ops reported](https://github.com/FreeRDP/FreeRDP/pull/13608#issuecomment-6131161999) 19–21 server FPS at 50% loss and 18–19 at 70%, using `d148cdb76` (FreeRDP 3.32.2 plus 39 PR commits). The [linked method](https://github.com/FreeRDP/FreeRDP/pull/13608#issuecomment-6131357705) is documented in the pinned [OpenThinRDP benchmark](https://github.com/OpenThinRdp/openthinrdp/blob/142434adf715c3f3352c0e6dd7b7ece90244aeec/tests/udp-bench/README.md).

| Parameter | PR's cited graphics method | Our frozen transport matrix |
|---|---|---|
| Peers | Windows server → Linux FreeRDP | Two PR native endpoints on Mac |
| Main traffic | Progressive graphics / coloured noise | Client-to-server CRC bulk + 20 Hz probes |
| Loss direction | Server-to-client only, including TCP and UDP | Independent UDP loss in both directions |
| Bandwidth | Uncapped | 10 Mbit/s each direction |
| Delay / reorder | Large packets: 1 ms and 70% reorder | 15 ms each way, ±1 ms jitter, no extra reorder |
| Queue | Netem limit 100,000 packets | 30 ms shaping queue |
| Trial | 120-second sequential ramp, stop on process exit | 5/30/12-second warmup/measurement/drain |
| Treatments | Default loss 50/70/80%; no explicit seeds or window sweep | Loss 0/25/50/70%, five seeds, four DATA limits |
| Metric | Server RemoteFX counters and process survival | Full-stream CRC/hash, probe RTT, service and native health |
| Revision | Reported `d148cdb76` | Measured `a306a67c1` plus diagnostic overlay |

The asymmetric method leaves client ACK traffic unimpaired. Our symmetric treatment also drops ACKs and retransmissions in the return direction. Windows supplies a different sender and recovery policy from the second PR endpoint in our raw test. The workload, sender, network, and acceptance criteria all differ.

[Microsoft defines server output FPS](https://learn.microsoft.com/en-us/azure/virtual-desktop/remotefx-graphics-performance-counters) as frames made available to the client, not physical client presentation. It does not certify CRC goodput or probe p95/p99. The pinned [OpenThinRDP UDP documentation](https://github.com/OpenThinRdp/openthinrdp/blob/142434adf715c3f3352c0e6dd7b7ece90244aeec/docs/udp.md) also limits the results to its particular setup and notes a TCP timeout after about 100 seconds in one 70% run versus a different run surviving 150 seconds. No quantitative 25% claim was found.

The [PR author's October 9 report](https://github.com/FreeRDP/FreeRDP/pull/13608#issuecomment-6085877061) is different again: 2% loss plus a two-second outage every 20 seconds, around 65 Mbit/s, with eight outages over 180 seconds without failure. ACK changes left server output roughly unchanged at 18.5 → 18.3 FPS.

Our failures do not directly refute those graphics results, and those FPS readings do not validate our raw transport matrix. The next measurement work should separate relay timing, observer coverage, and SUT status; support long waits without invalidating unrelated metrics; and use a validated kernel shaper or traced Mac relay. Checking the PR's claim directly requires the pinned Windows-to-Linux graphics method and matching revision, with client delivery and tunnel status measured alongside server counters.

No trial was rerun, and no frozen source, binary, sample, or export was rewritten. The per-trial breakdown is in [timing-cause-audit.json](timing-cause-audit.json).
